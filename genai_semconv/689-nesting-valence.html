GenAI semantic conventions review

is_nested or is_root?

Which value of the nesting boolean in #689 should be the one instrumentations must set. Follows up on #571.

Summary Terms Failure cases Proposal Alternatives

Summary

"root" comes out slightly ahead.

Both valences break when some instrumentation in the call chain doesn't set the attribute. They differ in where that instrumentation has to be for the end-to-end query to go wrong:

  • root is wrong only when an invocation above a participating one doesn't set it.
  • nested is wrong when any invocation that is actually nested doesn't set it, at any depth.

Every way root goes wrong, nested goes wrong too. The reverse doesn't hold.

An inner invocation doesn't set it

invoke_runner          8.0 s  sets it
└── invoke_workflow crew 2.0 s  doesn't

nested != true   # → {8.0, 2.0}  ✗
root == true     # → {8.0}       ✓

Under nested, the crew's point has no attribute and counts as top-level. Under root, it has no attribute and is left out.

An outer invocation doesn't set it

invoke_workflow graph   9.0 s  doesn't
└── invoke_agent Concierge 7.9 s  sets it

nested != true   # → {9.0, 7.9}  ✗
root == true     # → {7.9}       ✗

Concierge can't see the graph, so it reports itself as top-level under both. Both results are wrong.

What root costs

An app whose only instrumentation doesn't set the attribute gets no points from root == true; nested counts it correctly because nothing is nested. Root's failure here is an empty series rather than a wrong number. Lost context (case 4) and cross-process calls (case 8) break both the same way.

Terms click to expand

▶
Participating instrumentation — Writes the shared invocation key into context, reads it, and sets the attribute. Anything else emits the metric with the attribute absent.

Non-participants today include ADK and Agent Framework native instrumentation (per the #689 description), every instrumentation version released before the attribute, and any framework that never adopts it.

▶
Shared context key — For one vendor to see another's invocation, both must use the same key. In Python, Java and Go that means a shared package.
 
# opentelemetry-api, Python
def create_key(keyname: str) -> str:
    return keyname + "-" + str(uuid4())

# opentelemetry-java: ContextKey.named
# "Multiple different keys with the same
#  name will be separate keys."

# opentelemetry-js: createContextKey
return Symbol.for(description);  # shared by name

Only JS shares keys by name. Elsewhere vendors need a common package (or, in Python, an agreed raw string passed to get_value).

reference_shared.py on the PR branch uses context.create_key("gen_ai.invocation"). That works because every scenario imports the same module; no other package could read the key.

This cost is the same under both valences. What differs is who has to pay it for the dashboard to be correct.

▶
Positive vs negative evidence — "Nested" means the key was seen. "Top-level" means it wasn't. is_root=true and is_nested=false are the same claim.

Seeing the key is reliable: some participating invocation is active. Not seeing it only means no participating invocation is active. That is the concern behind "don't promise what we can't guarantee (false)".

Reversing the valence doesn't make that claim stronger. It changes what absence is lumped with. Under is_nested, absent means "top-level or unknown". Under is_root, absent means "doesn't participate".

▶
Lenient vs strict filter — is_nested != true keeps absent points; is_nested == false drops them.

#689's motivation section prescribes the lenient filter. The strict filter matches is_root == true, but under #689 false is optional, so it returns little data.

▶
Loud vs silent failure — A missing series is noticed and traced to a missing integration. A skewed percentile looks like a real number.

Points are dropped per instrumentation, not at random: either all of an agent's top-level points carry the attribute or none do. So a dropped series is complete or empty, and an empty one is easy to spot.

Extra points are worse: metrics have no parent link, so the consumer can't remove them afterwards.

▶
1 · O and I participate — The case #689's reference scenarios cover. Both valences work.
 
invoke_runner               # key absent → top-level
└── invoke_agent Concierge  # key present → nested

The strict #689 filter only works if the runner sets is_nested=false, which #689 allows but doesn't require. Its reference scenarios never set it (nested_invocation_attributes() "is never set to false").

▶
2 · I doesn't participate — A crew inside a tool, a native-instrumented agent inside a participating runner, an old instrumentation version. The case that decides the valence.
 
invoke_runner          8.0 s  participates
└── …
    └── invoke_workflow crew 2.0 s  absent

# #689 lenient   {8.0, 2.0}  ✗
# reversed       {8.0}       ✓

Under #689 the crew's point is indistinguishable from a top-level run. Request count doubles and the mean drops from 8.0 s to 5.0 s. The dashboard gives no sign that anything is wrong.

#689 says pydantic-ai, crewai and autogen don't set the attribute because "every invocation is top-level". That holds in the scenarios, not in general: any of them can run inside a tool or a graph node.

▶
3 · O doesn't participate — The gap you raised: an invocation above that isn't in the contract. Neither valence fixes it.
 
invoke_workflow graph       9.0 s  absent
└── invoke_agent Concierge  7.9 s  sees no key

# #689 lenient   {9.0, 7.9}  ✗ both
# #689 strict    {7.9}       ✗ wrong layer
# reversed       {7.9}       ✗ wrong layer

Concierge sees no key and calls itself top-level. The reversed valence gives one point per request, from the wrong layer. #689 lenient gives two. Docs should define the claim as "outermost participating invocation" so consumers know this limit.

▶
4 · Context lost between O and I — Thread pool without context copy, a callback registry, a queue. I looks top-level under both.
 
invoke_runner                 # writes key
  executor.submit(sub.run)     # no copy_context()
    invoke_agent Researcher   # key absent

This is the "context propagation is tricky" concern from review. It hits both valences the same way, because both read the same key. The broken span parent link is the same bug, so fixing traces fixes this too.

▶
5 · Single layer, doesn't participate — A plain pydantic-ai app. The one case where #689 lenient is better.
 
invoke_agent assistant   3.0 s  absent

# #689 lenient   {3.0}  ✓
# reversed       {}     ✗ until adopted

#689 gets this right only because nothing is nested. The same app gets case 2 as soon as a sub-agent is added. Under the reversed valence the dashboard is empty, and the fix is to upgrade the one instrumentation that owns it.

▶
6 · Nothing participates — Every deployment on the day the attribute merges.

Under #689 a dashboard built on is_nested != true returns exactly today's mixed histogram, and looks as if it applies a filter. Under the reversed valence it is empty until the outermost layer adopts.

▶
7 · SQL vs PromQL — Backends treat a missing attribute differently under !=.
 
# PromQL: a matcher that matches "" also selects
# series without the label
{is_nested!="true"}       # keeps absent

# SQL: NULL != TRUE is NULL, row dropped
WHERE is_nested != TRUE   # drops absent
WHERE is_nested IS DISTINCT FROM TRUE  # keeps

The same lenient filter silently turns strict in BigQuery- or ClickHouse-style backends. is_root == true means the same thing in both: absent never matches.

▶
8 · A2A server across processes — Scoped to the process by design, so the server-side agent is top-level under both.

A dashboard that aggregates across services counts the client's run and the server's run. Fixing that would need the flag in baggage, which is out of scope for both.

Who has to adopt for the dashboard to be right

#689 (lenient filter)

The outermost layer writes the key, and every nested layer reads it and sets true. One holdout anywhere below skews the result.

The nested components do the work; the owner of the outer dashboard gets the benefit.

reversed

The outermost layer writes the key, reads it, and sets true. Nested non-participants are harmless. Nested participants must read the key to avoid case 3, which they do by definition.

The component that wants end-to-end points does the work.

Proposal

1. The value the query selects is the value instrumentations must set

The query selects top-level invocations, so true means top-level.

2. Define true as "no participating invocation is active"

That is the check an instrumentation can actually perform, so it promises nothing it can't deliver. Cases 3 and 4 are then documented limits, not violations.

3. Participants set both values

false rests on positive evidence, so it is always safe. With both set, absent means "doesn't participate", and consumers can query sub-agent latency with == false.

# model/gen-ai/registry.yaml
- key: gen_ai.request.is_nested+ key: gen_ai.request.is_root  type: boolean
+ brief: Whether no other agent invocation is active in the process.  note: |
+   `true` when no other `invoke_agent`, `invoke_workflow`, or+   `invoke_{framework_entrypoint}` invocation tracked by an instrumentation+   is active in the same process; `false` when one is.++   Invocations made by code that doesn't track invocations aren't visible,+   so `true` doesn't guarantee there is no invocation further up.    # + the existing SHOULDs on tracking in shared context keys

# model/gen-ai/spans.yaml, model/gen-ai/metrics.yaml
- ref: gen_ai.request.is_nested-   conditionally_required: When the invocation is nested.+ ref: gen_ai.request.is_root+   conditionally_required: When the instrumentation tracks active invocations.

Consumer guidance

End-to-end durations: is_root == true. Absent means the instrumentation doesn't track invocations; don't treat it as either value.

Name

"Root" already means the trace root span, and ADK's root_agent, which is nested when run through AgentTool. is_top_level (the wording #689's note already uses) avoids both.

same tracking mechanism as #689 reference: flip the helper, set both values cost: non-nesting libraries must adopt to appear

Alternatives considered

A

#689 as is: is_nested, conditionally required when nested

Asserts only what it has positive evidence for. The cost lands on consumers: the obvious filter counts every non-participant as top-level.

✓ single-layer apps work without adopting ✗ case 2 skews silently ✗ backend-dependent !=
B

is_nested, set both ways by participants

Carries the same information as the proposal. Consumers who use == false get the proposal's behavior; those who write the more obvious != true or NOT is_nested still get case 2. The safe query is the less obvious one.

✓ smallest change to #689 ✗ correctness depends on the consumer picking the strict filter
C

Integer depth, 0 = top-level

depth == 0 drops absent points like the proposal. But depth counts only participating layers, so values above 0 vary with which frameworks adopted, and each level is another series.

✓ fails loud ✗ depth > 0 unreliable ✗ more series
D

Derive end-to-end duration from spans

Span parent links already separate the layers, so a span-to-metrics pipeline can keep only spans whose parent isn't an invoke_*. That needs every invoke_* span exported unsampled, which the duration metric exists to avoid. Context loss (case 4) breaks it too.
