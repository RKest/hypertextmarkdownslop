Shared Concept Naming Matrix: Workflows, Agents & Single LLM/Tool Calls

Analysis of all 10 documentation ecosystems linked in the OTel LLM SemConv WG #571 Naming Doc . Each cell in the matrix is a single 3-slice circle grading whether a term is used for:

  • Top-Left Slice (Workflow / Multi-Agent): Green = Term used to refer to workflow / multi-agent orchestration · Red = Not used.
  • Top-Right Slice (Agent): Green = Term used to refer to a single agent (running inference + 0..N tool calls) · Red = Not used.
  • Bottom Slice (Single LLM / Tool Calls — Inverse): Green = Term NOT used to refer to single LLM/tool calls (good—no collision!) · Red = Term IS used to refer to single LLM/tool calls (bad—collides with atomic calls).
How to Read Each Circle
↖ Top-Left: Term (not) used to refer to workflow / multi-agent (used = 🟢, not = 🔴)
↗ Top-Right: Term (not) used to refer to agent (used = 🟢, not = 🔴)
↓ Bottom (Inverse): Term (not) used to refer to single LLM/tool calls (not used = 🟢, used = 🔴)
● All 3 Slices Green (3/3) = Ideal Shared Term
1. Most All-Green (3/3) Circles
Loop (4× 3/3 All-Green)

Loop (Agent Loop / Core Reasoning Loop) achieves a full 3/3 Green circle in OpenAI Agents SDK, Google ADK, Anthropic, and Decagon, and its bottom slice is Green in all 10/10 docs (never conflated with a single LLM or tool call).

2. Runners-Up for 3/3 All-Green
Run (3× 3/3) & Orchestration (3× 3/3)

Run is 3/3 All-Green in OpenAI Agents, Gemini Enterprise, and Decagon (and covers Workflow + Agent in ADK & MAF, where tools also have a red bottom slice). Orchestration is 3/3 All-Green in ADK, AWS Bedrock, and Azure Foundry.

3. Top-2 Green, Bottom Slice Red
Step (5× Top-2 🟢) · Invocation & Execution (3×)

Step (in 5 docs) and Invocation / Execution (in 3 docs) cover both Workflow and Agent (top two slices Green), but always turn the bottom slice Red because those same docs also use them for atomic LLM/tool calls.

4. All-Red (0/3) Collisions
Invocation (5× 0/3) & Execution (2× 0/3)

In Paper Compute, OpenAI Agents, Anthropic, Decagon, and A2A, Invocation is 0/3 All-Red: not used for workflows, not used for agents, and used specifically for single LLM/tool calls.

2. Notable Umbrella / Architectural Terms in Specific Documentations

Specialized terms coined or elevated by individual documentations to unify or separate these layers:

Agentic System (Anthropic) 3/3 🟢

Anthropic explicitly coins "agentic systems" as the umbrella noun covering both deterministic workflows ("where LLMs and tools are orchestrated through predefined code paths") and dynamic agents ("where LLMs dynamically direct their own processes and tool usage").

anthropic.com/research/building-effective-agents ↗
Core Reasoning Loop (Decagon) 3/3 🟢

Decagon explicitly defines a "core reasoning loop" as the component that "Drives the dynamic work—whether structured as a single LLM call, a ReAct (Reason+Act) loop, or multi-agent orchestration."

decagon.ai/glossary/what-is-an-agent-workflow ↗
Trace (OpenAI Agents SDK) 3/3 🟢

In OpenAI Agents SDK, a Trace wraps every Runner.run() execution block and represents a single end-to-end operation of a workflow spanning model generations, tool calls, and multi-agent handoffs.

openai.github.io/openai-agents-python/tracing/ ↗
Harness / HarnessAgent (MAF & Vertex) 2/3 · Agent only

Microsoft Agent Framework defines an Agent Harness (HarnessAgent) as the batteries-included runtime scaffolding bundling an automatic tool-calling loop, planning, and compaction for a single agent.

learn.microsoft.com/en-us/agent-framework/concepts/agents ↗
Routine (Azure AI Foundry) 2/3 · Agent only

Azure AI Foundry defines Routines as a strict one-trigger, one-action automation for invoking a single agent, explicitly contrasting them with multi-agent Workflows.

learn.microsoft.com/.../concepts/routines ↗
Agent Tree vs Turn (Paper Compute) 2/3 · Split

Paper Compute strictly separates single-agent work (an Agent Turn containing an Execution Trace of model invocations and tool calls) from multi-agent delegation (an Agent Tree spawning child sessions).

papercompute.com/concepts/agent-turns/ ↗

4. Architectural Summary per Documentation Source

Paper Compute (Agent Turns)

Paper Compute's 'Agent Turns' documentation (under its 'Foundations: Agents — Four interactive lenses on one specimen session' series) presents a clear, layered decomposition of agent execution. Crucially, Paper Compute deliberately avoids overloading a single umbrella term across multi-agent workflows and single-agent loops. A single agent's execution between conversation boundaries is modeled strictly as an 'Agent Turn' (which encapsulates an inner 'execution trace' of zero or more 'model invocations', tool requests, tool results, and state changes). Conversely, multi-agent control flow is conceptualized as an 'Agent Tree' ('Your Agent Is a Tree, Not a Chat'), where subagent delegation does not append to the parent's turn or chat, but instead spawns an isolated 'session' with its own turns, tools, context, and cost before returning a summary. Consequently, terms like 'Turn', 'Invocation', and 'Execution' (execution trace) are RED (strictly single-agent control flow), while 'Tree' is RED (strictly multi-agent delegation). No term in Paper Compute spans both multi-agent workflow orchestration and the single-agent loop.

OpenAI Agents SDK & API

In OpenAI Agents SDK & API, the central unified execution concept spanning BOTH multi-agent workflows and single-agent execution is 'Run' (via the 'Runner' class, e.g. Runner.run, Runner.run_sync, Runner.run_streamed) and its underlying 'Agent Loop'. When Runner.run is called, the agent loop executes a continuous cycle: invoking the LLM, executing any requested tool calls and re-running the loop (single-agent loop), and/or switching active agents when a handoff occurs and re-running the loop (multi-agent orchestration). In contrast, 'Orchestration' and 'Workflow' are used specifically for multi-agent coordination (via code or handoffs), while 'Turn' specifically denotes a single AI model invocation cycle (including its tool calls) or a single cycle of work in a session.

Microsoft Agent Framework

Microsoft Agent Framework (MAF) differentiates between single-agent autonomous execution (AIAgent, ChatClientAgent, HarnessAgent) and multi-agent / deterministic orchestration (Workflows, Executors, Edges, Supersteps). The primary shared execution concepts encompassing BOTH single-agent model/tool loops and multi-agent/workflow graphs are 'Run' (agent.RunAsync / InProcessExecution.RunAsync), 'Execution' (agent execution vs. workflow BSP superstep execution), and 'Invocation' (invoking an agent / FunctionInvocationContext vs. workflow_invoke / ExecutorInvokedEvent / invoking agents as tools). Concepts like 'Orchestration', 'Workflow', 'Step', and 'Executor' are exclusive to multi-agent/workflow coordination, while 'Agent', 'Harness', and 'Agent Loop' are exclusive to single-agent execution.

Google ADK (Agent Development Kit)

In Google ADK (Agent Development Kit), the architecture is centered around BaseAgent subclasses (both intelligent LlmAgent and deterministic WorkflowAgent subclasses like SequentialAgent, ParallelAgent, and LoopAgent) running within an Invocation managed by a Runner. The documentation uses several concepts symmetrically across both multi-agent/workflow orchestration and single-agent execution loops: Orchestration, Invocation, Run, Agent, Execution, Task, Step, and Interaction are all used for both. In contrast, 'Workflow' is used strictly for deterministic multi-agent and graph control flows (explicitly contrasted with non-deterministic LlmAgent execution), and 'Turn' is used to represent a conversational interaction between user and agent within which multiple steps or agents execute.

Anthropic Claude Docs (Tool Use, Workflows, Managed Agents)

Anthropic's architectural documentation makes a strict conceptual distinction between Workflows (systems where LLMs and tools are orchestrated through predefined code paths) and Agents (systems where LLMs dynamically direct their own processes and tool usage in a loop). The explicit overarching umbrella term used by Anthropic to encompass both is 'Agentic Systems'. In Claude Managed Agents, 'Session' also functions as an umbrella runtime primitive for both single-agent and multi-agent coordination. Among the evaluated candidate terms, 'Step' is GREEN as it is explicitly used to describe execution increments in both deterministic workflows (prompt chaining steps) and single-agent loops (environment ground-truth steps). Terms like 'Orchestration' and 'Workflow' are RED because Anthropic strictly associates them with predefined code paths and multi-agent systems, explicitly contrasting them with autonomous agent loops. Conversely, 'Turn' and 'Run' (via Tool Runner) are RED because they describe conversational/SDK message and tool execution cycles for single agents rather than workflow orchestration.

Decagon (Agent Workflow Glossary)

Decagon's AI and CX glossary centers its execution model on 'Workflow' (or 'Agent Workflow'), defined as 'the ordered sequence of reasoning steps, tool invocations, and decisions an AI agent executes to complete a task' spanning from 'fully scripted graphs where each step is predetermined to fully dynamic sequences where the LLM chooses the next step at runtime.' Decagon also introduces 'Core Reasoning Loop' as an explicit umbrella concept that drives dynamic work across a single LLM call, a ReAct (Reason+Act) loop, or multi-agent orchestration. Concepts like 'Workflow', 'Step', 'Run', and 'Task' are shared across both single-agent control loops and multi-agent/graph workflows, whereas 'Orchestration' is specifically positioned as the coordination layer sitting above individual agents, 'Invocation' is used for tool/model invocations, and 'Turn' and 'Interaction' describe user-facing conversational exchanges rather than execution control flow.

Google Gemini Enterprise Agent Platform (Vertex AI / Reasoning Engine / Interactions API / Agent Registry)

Google Gemini Enterprise Agent Platform (formerly Vertex AI Agent Engine / Reasoning Engine, unified with the Interactions API and Agent Registry) uses 'Workflow', 'Turn', 'Run', and 'Execution' across both multi-agent/graph orchestration and single-agent loops. Specifically: (1) 'Workflow' is used for multi-agent frameworks (AG2/LangGraph) and explicitly defined in Agent Registry as 'A sequence of steps where an AI agent independently determines tool usage, reasoning, and execution paths to accomplish a task'; (2) 'Turn' bridges multi-agent conversational turns (AG2) and single-agent tool execution steps ('one turn to generate tool arguments and a second to execute the tool'); (3) 'Run' (/api/run and runner.run) executes both multi-agent orchestrator hierarchies and single-agent inference loops; (4) 'Execution' spans runtime execution services and single-agent execution logic/traces. Meanwhile, 'Interaction' and 'Step' specifically define single-agent control flow in the Interactions API, whereas 'Orchestration' and 'Task' (via A2A protocol) specifically define multi-agent coordination.

AWS Bedrock Agents & Bedrock AgentCore Runtime

AWS Bedrock and Bedrock AgentCore Runtime distinguish between single-agent reasoning/action loops (handled by Bedrock Agents and AgentCore Runtime via an 'orchestration step' and ReAct framework) and multi-agent / deterministic graph workflows (handled by multi-agent collaboration with supervisor/collaborator agents and Amazon Bedrock Flows). The terms 'Orchestration', 'Invocation', and 'Step' are shared across BOTH single-agent loops and multi-agent/workflow control flow: Bedrock uses 'Orchestration' both for multi-agent supervisor coordination and for the single-agent reasoning/tool execution loop; 'Invocation' for the InvokeAgent/InvokeFlow APIs as well as within OrchestrationTrace (InvocationInput) covering both action group tool calls and agent collaborator handoffs; and 'Step' for individual nodes in Flows as well as the 'orchestration step' in an agent's reasoning loop. 'Workflow', 'Execution', and 'Agent' are RED (used for only one domain), while 'Run', 'Turn', 'Task', and 'Interaction' are NONE (not used as formal control-flow concepts).

Azure AI Foundry Agent Service & Hosted Agents

Azure AI Foundry Agent Service and Hosted Agents delineate execution concepts clearly between two levels: (1) Single-Agent Execution: The Agent Service uses 'Run' (with fine-grained 'RunStep' entries for model calls and tool executions) on top of persistent 'Threads', while Hosted Agents use the 'Responses Protocol' (OpenAI-compatible) or 'Invocations Protocol' (custom payloads/webhooks via POST /invocations and GET /invocations_ws). (2) Multi-Agent / Graph Orchestration: Handled via 'Workflows' (sequential, concurrent, or group-chat multi-agent graphs) and 'Agent-to-Agent (A2A)' communication tools/protocols. Across both levels, 'Orchestration' is the predominant conceptual umbrella term covering both an agent's internal loop ('custom orchestration logic', 'runtime loop that manages execution, model turns, and tool integration') and multi-agent coordination ('multi-agent orchestration patterns'). 'Step' is also used at both tiers ('RunStep' for tool-call/message items in a run, and workflow 'steps' in multi-agent pipelines). In contrast, 'Run', 'Invocation', 'Turn', and 'Workflow' are strictly scoped to one tier or the other.

A2A Protocol (Agent2Agent Specification)

The Agent2Agent (A2A) Protocol is an open standard designed to enable interoperability, discovery, and collaboration between independent AI agents across different frameworks and vendors. Its architecture is structured into three layers: Layer 1 Canonical Data Model (defined normatively in a2a.proto with core entities AgentCard, Task, Message, Artifact, and Part), Layer 2 Abstract Operations (SendMessage, SendStreamingMessage, GetTask, CancelTask, etc.), and Layer 3 Protocol Bindings (JSON-RPC over HTTP, gRPC, HTTP+JSON/REST). A core design tenet of A2A is 'Opaque Execution', where remote agents are treated as black-box systems whose internal memory, prompts, and toolchains remain hidden. A2A explicitly contrasts itself with protocols like the Model Context Protocol (MCP): MCP operates vertically (connecting an individual agent downward to local tools and resources), whereas A2A operates horizontally (connecting independent agents across enterprise boundaries to delegate tasks and exchange artifacts). Because A2A deliberately avoids standardizing or inspecting the internal execution loop of a single agent (inference + tool calls), there is NO shared umbrella term in A2A that encompasses both multi-agent/workflow orchestration and single-agent tool loops. Concepts like Task, Message, Turn, Workflow, and Orchestration apply strictly to horizontal inter-agent communication, while single-agent execution is encapsulated locally behind an opaque AgentExecutor interface.
